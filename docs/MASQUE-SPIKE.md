# MASQUE-SPIKE — карта решения (TZ-04-20260930 §3.7) · 2026-09-30

**Контекст.** `handleMASQUE` сегодня отвечает честным `501 Not Implemented`. MASQUE
(IP-proxying over HTTP/3, RFC 9484) — третий транспорт поверх quic-go рядом с
onion+WT-egress. Вопрос: стоит ли bump quic-go и реализовывать, или зафиксировать 501.

## Варианты

| Вариант | Что даёт | Цена/риск | Балл (вес) |
|---|---|---|---|
| **A. Оставить 501 (статус-кво)** | Ноль работ; WT+onion уже покрывают egress | MASQUE-клиентов не обслуживаем (пока их нет и в планах нет) | 8 |
| **B. bump quic-go + MASQUE-connect** | Полный RFC 9484 CONNECT-UDP proxy | quic-go мажорные брейки API (v0.6x серия); регресс WT-пути; 2–4 хода; аудит TLS/ACL заново | 4 |
| **C. HTTP/3-relay без MASQUE** (сырые CONNECT-UDP в своём формате) | Совместимость с нашим же клиентом | Не-стандарт; смысл только если появятся клиенты, которым MASQUE не нужен | 5 |

## Ключевые факторы

1. **Потребитель отсутствует.** Android/PWA/desktop используют onion/WT; MASQUE в
   бэклоге ни одной задачи (v6, блок Messenger/VPN — нет MASQUE).
2. **Риск регресса велик.** `webtransport_server.go` + nip59 + exit-auth сидят на
   текущем quic-go; bump ради нереализованной фичи — типичный «decided ≠ needed».
3. **501 — честный контракт.** Клиент получает внятный отказ, не таймаут.

## Рекомендация

**Вариант A**: зафиксировать 501 документально (этот файл + строка в WIRE-SPEC §7),
вернуться к MASQUE только когда появится реальный потребитель (внешний клиент/стандарт-
интероп). Условие reopening: задача в бэклоге v6 с user_value ≥ 8 от реального сценария.

**Не развилка для Choser-таблицы**: выбора с конкурентными плюсами нет — потребитель
отсутствует, argmax очевиден; карточка не строится (нет 5+ живых вариантов).
